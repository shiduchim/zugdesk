# FINAL-01 — Build and review checklist

- All five companion deliverables open independently on phone and desktop and use fictional example people only.

- The Offers card renders fields defined in the approved Add Person intake. Missing facts are not silently completed. A saved name is not automatically a formal offer.

- The My Profile Share action may prepare or copy an approved profile; private notes, unrelated contacts and recorded feedback must never leak into shared content.

- A contact can be pinned or moved to an optional folder without duplicating the person. Search, Sort, Filters and the selected person survive Contacts layout changes in the production implementation.

- Theme / density choices adjust visuals only and do not mutate people, shidduchim, notes, contact relationships or history.

- Run touch and keyboard checks at 320, 360, 390 and 430 px; test long Hebrew text, right-to-left layout and accessibility.

- Keep Home v8 and the approved Shidduchim / Add Person prototypes intact until a deliberate integration into the actual ZivugMatch application.

# FINAL-02 — Companion HTML status

The delivered HTML files are standalone design references, not a synchronized production application. The original Claude My Profile exports are preserved byte-for-byte. The Offers prototype has fictional Add Person data and its own local demo behavior; it is not the live data store. Contacts layouts is a separate comparison prototype. No new theme system is provided.

# FINAL-03 — Design source priority

When references disagree: preserve the latest explicitly approved functional behavior, then use the latest named design reference for appearance. Proposed improvements are not automatically approvals. Keep historical originals and change records accessible, and require an explicit review before replacing the approved source screens.
